# Atom63 production readiness audit

**Milestone:** 1 — Production readiness audit

**Audit date:** 2026-09-19

**Scope:** `@atom63/styles`, `@atom63/ui-foundation`, `@atom63/ui-react`, the design-system docs app, Storybook, and the Figma plugin

**Decision:** The repository has a strong executable design-system core, but it is not ready to promise a public stable API or a code/Figma source of truth. Complete the token manifest and package-consumer proof before expanding the public surface.

This report summarizes deterministic inventories generated by `scripts/design-system/audit-package-surface.mjs`. The component-stability and token/Figma-surface audits it originally cited were retired on 2026-09-24; Figma coverage is now checked by the generated Figma sync model (`pnpm --filter @atom63/styles check:figma`).

The corresponding JSON evidence lives in `docs/design-system/audits/`. Counts are derived from the current repository rather than maintained by hand. The component lifecycle recommendation is a structural candidate, not a semver commitment: authored guidance, accessibility review, visual regression, and external-consumer evidence remain separate release gates.

Milestone 2 now also generates the canonical CSS declaration inventory at `packages/styles/generated/atom63.tokens.json` and the Figma sync model at `packages/styles/generated/atom63.figma-sync.json`. Both are regenerated from source.

## 1. Current assets

Atom63 already has the main parts of a production design-system platform:

- Three publishable package manifests: `@atom63/styles`, `@atom63/ui-foundation`, and `@atom63/ui-react`.
- A CSS-first token and contract system with 36 audited CSS source files and 1,015 unique custom properties across token and contract layers.
- A React renderer with 68 root-exported component families, co-located Storybook stories, focused tests, CSS recipes, and generated public reference pages.
- A private design-system documentation app with foundation, component, pattern, product, theme, and architecture content.
- A private Storybook app for exhaustive component inspection.
- A private Figma plugin with token/style import and export, styleguide UI, component generation, and variable rebind workflows.
- Changesets, monorepo CI, package-boundary checks, typechecking, linting, tests, and builds.

These are substantial assets. The gap is not a lack of components or tooling; it is the absence of one governed public contract connecting those assets.

## 2. Package readiness

The package audit covers six surfaces. Three are publishable libraries and three are intentionally private applications.

| Package | Private | Export entries | Files whitelist | Side effects | Quality scripts |
| --- | ---: | ---: | --- | --- | --- |
| `@atom63/styles` | No | 58 | `generated`, `src` | CSS | lint, test |
| `@atom63/ui-foundation` | No | 1 | `dist` | `false` | build, lint, typecheck |
| `@atom63/ui-react` | No | 70 | `dist`, source CSS | CSS | build, lint, test, typecheck |
| `@atom63/design-system` | Yes | 0 | — | — | build, lint, test, typecheck |
| `@atom63/figma-plugin` | Yes | 0 | — | — | build, lint, font test, typecheck |
| `@atom63/storybook` | Yes | 0 | — | — | build, lint, typecheck |

Positive evidence:

- The three library manifests have explicit export maps and files whitelists.
- `@atom63/ui-react` declares only React and React DOM as peers; its runtime dependencies are explicit.
- CSS side effects are declared for the packages that ship executable styles.
- The docs, Storybook, and Figma surfaces remain private, so they do not accidentally become unsupported package APIs.

Readiness gaps:

- None of the six audited manifests declares `publishConfig.access`; the root Changesets configuration still uses `"access": "restricted"`.
- The general Changesets workflow prepares version PRs but intentionally does not publish. The only public npm release workflow is specialized for the slides toolchain.
- There is no design-system package pack audit, packed-tarball inspection, or clean external install smoke test.
- `@atom63/styles` has no build or typecheck script. That may be correct for a source-CSS package, but publication still needs a pack-level validation of every exported target.
- Package lifecycle, support level, ownership, and deprecation policy are not machine-readable.

## 3. Component maturity

The component audit found 69 direct source directories. Of those, 68 are exported from the `@atom63/ui-react` root and represented in the generated component catalog. The remaining `menu` directory is an internal shared implementation: it has a story but no root export, focused test, or catalog record.

| Evidence | Count |
| --- | ---: |
| Direct component source directories | 69 |
| Root-exported component families | 68 |
| Generated catalog/reference families | 68 |
| Families with at least one story | 69 |
| Families with a focused test | 68 |
| Families with a published recipe CSS entry | 61 |
| Authored `component-*.mdx` pages | 8 |
| Authored pages tied to a component family | 6 |

Using the audit's structural rules, 68 families are stable candidates, zero are preview candidates, and `menu` requires internal review. That result reflects the current catalog's blanket `stable` status plus story/test/export coverage. It should not be interpreted as a public stability declaration yet.

The largest maturity gap is documentation depth. Six component families have authored decision guidance (`button`, `button-group`, `dropdown-menu`, `input`, `segmented-control`, and `tabs`); the other 62 rely on generated references. `component-overview.mdx` and `component-contract.mdx` are section-level pages rather than component-family overrides. Generated references provide discoverability, but they do not by themselves establish support boundaries, accessibility expectations, non-usage guidance, migration commitments, or Figma parity.

Recipe CSS is intentionally not a universal stability gate. Eight records lack a slug-specific published recipe entry: `animated-check`, `destination-link`, `menu`, `portal-container`, `progressive-blur`, `search-field`, `spinner`, and `toaster`. Some are composition or provider surfaces, and menu CSS is shared by context-menu and dropdown-menu exports. Each exception still needs an explicit classification so consumers can distinguish intentional absence from incomplete packaging.

## 4. Token/Figma parity

The token and Figma audit is the clearest release blocker.

| Evidence | Count |
| --- | ---: |
| CSS token source files | 18 |
| CSS contract source files | 18 |
| Unique CSS custom properties | 1,015 |
| Generated Figma preset entries | 359 |
| Unique CSS names represented by the preset | 150 |
| CSS variables with no preset entry | 871 |
| Preset entries with no CSS declaration | 6 |
| Preset entries whose source file is missing | 0 |

The preset now consumes `packages/styles/generated/atom63.tokens.json` and keeps a deliberately curated bridge equivalent to the previous `brand.css`, `semantics.css`, `surface.css`, `radius.css`, and `type-scale.css` boundary, then adds compatibility scales. Its 359 entries collapse to 150 unique CSS names because theme/mode declarations repeat names with different values. The 871 variables outside the preset include foundation and contract surfaces, so the current preset remains a curated Figma sync surface rather than the full canonical manifest.

The six preset-only names are compatibility size variables generated inside `generate-atom63-preset.ts`; they use `apps/figma-plugin/scripts/generate-atom63-preset.ts#compat` provenance rather than pretending to come from CSS declarations. This is valid current behavior and should eventually move into explicit manifest compatibility metadata.

All five audited Figma capabilities are present:

- variable and style import;
- variable and style export;
- styleguide UI;
- component generation;
- scan/apply rebind.

However, the component generator still imports recipes from `@atom63/cipher-boilerplate`, identifies that package as its component source, and contains hardcoded color, baseline-scale, font, radius, and dimension fallback candidates. Those values can drift from `@atom63/styles` and `@atom63/ui-react`. A canonical manifest must replace those duplicated defaults and give the generator a supported Atom63 component mapping.

## 5. Docs and adoption gaps

The documentation app already explains architecture, foundations, themes, components, product-scale usage, and the Cipher workflow. It also generates a reference route for every public component family. This is a strong maintainer and evaluator surface.

It is not yet a complete external adoption path. The current page inventory does not provide a single explicit installation/quickstart flow, a package-by-package public API reference, a lifecycle/stability policy, a Figma setup and synchronization contract, or a migration/deprecation policy. There is an existing `apps/fixture-vite`, but no clean `examples/vite-basic` consumer that installs packed artifacts as an external project would.

Until that path exists, workspace builds can pass while published tarballs, export maps, CSS inclusion, peer requirements, or first-run documentation remain broken for a real adopter.

## 6. Release and governance gaps

Existing CI is broad and valuable: affected package checks, nightly full lint/typecheck/test/build, architecture guardrails, routing checks, package governance, token checks, and bundle-size checks already reduce regression risk.

Production design-system release discipline still needs:

- a public-access decision reflected consistently in Changesets and package manifests;
- a DS-specific release workflow with packages published in dependency order;
- `npm pack` inspection for all three public packages;
- a clean install/build smoke test using packed tarballs rather than workspace links;
- provenance and registry policy for public publication;
- machine-readable package, token, and component lifecycle metadata;
- a deprecation and migration policy;
- ownership and release acceptance criteria that connect code, docs, tests, and Figma parity.

No API changes should be made until these contracts identify which current surfaces are stable, preview, internal, or deprecated.

## 7. Recommended milestone order

1. **Canonical token manifest.** Define schema, provenance, lifecycle, modes, aliases, and validation; generate CSS/Figma/docs views from it or audit them against it.
2. **Figma alignment.** Move the preset and component generator from curated/hardcoded fallbacks to the manifest, then record component-to-Figma parity explicitly.
3. **Package readiness.** Decide public access, verify every export in packed artifacts, and add an external install smoke test.
4. **Adopter docs and examples.** Ship installation, quickstart, package reference, lifecycle, Figma workflow, and a clean Vite example using packed packages.
5. **Core component stabilization.** Publicly commit only a deliberately small core whose authored guidance, accessibility, visual coverage, Figma status, and migration contract pass the gate.
6. **Release governance.** Add the DS release train, provenance, ownership, changeset policy, deprecation workflow, and recurring drift audits.

The biggest remaining issue is component-generation drift: canonical token provenance now feeds the Figma preset, but the component generator still carries its own `@atom63/cipher-boilerplate` recipe source and hardcoded fallback values. Milestone 3 should replace those duplicated defaults with manifest-backed component/token mappings before package or component stability promises are expanded.
