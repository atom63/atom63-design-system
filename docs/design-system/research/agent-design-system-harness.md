# 先把护栏装进使用方项目，再谈分发

> 调研日期 2026-10-09，范围：agent 用设计系统的格局、AI 视觉漂移的度量、设计师认可的 token 架构。文中的 F1–F4 是调研时的阶段草案，定稿的阶段和决策见 [`../roadmap-next.md`](../roadmap-next.md)。

**结论：** 三条研究线指向同一个方向。下一阶段的重心应从“让 agent 知道 Atom63”转到“让 agent 写错时被确定性地拦住”，而且先拦在维护者自己的产品仓库里。2026 年，检索层（MCP、CLI、manifest、模板检索）已经普及。Meta 的 Astryx 几乎一比一实现了 Atom63 的“检索 + 硬规则 + vibe test”模式，但它自己的夜间账本里，基线赢了 50 次，Astryx 只赢 19 次。能实测降低漂移的是 lint 反馈：`@shadcn/lint` 的评测里，五个模型的违规数加上反馈后都降到 0。VLM 评审的可靠性只够当参考：成对判断约 60%，接近抛硬币，所以 `atom63 review` 不能拿它当门禁。现在 4 个 brief 各跑一次的 vibe test，在统计上证明不了任何结论。token 架构方面，shadcn 角色名的价值在于生态兼容，没有证据说它能提高 agent 的准确率。Figma 侧的重分层方向正确，但要受套餐上限约束，改名也会断引用；DTCG resolver 的工具支持还很薄，所以 Atom63 必须保留自己的生成器。按项目目标排序（目标 2 和 1 优先于 3，见路线图的前提），F2 应该前移，但它前面要先完成一个缩小版 F1，把语义词汇冻结、把 token 轴正交化，因为 lint 会把词汇固化下来。F4 只做套餐允许的部分，F3 退到最后。这里的证据多数来自单一审计者、厂商自报或小样本，下文会逐条标出。

## 检索已成标配，确定性门禁仍是空位

2026 年 7 月，有人横向审计了 21 个主流设计系统：**20 个有 MCP server，19 个有 agent skill，15 个有 llms.txt**；统计到的“验证循环”技术有 31 条，但大多是告诉 agent 去跑的检查，而不是写进使用方 CI 的门禁（[State of AI in DS](https://state-of-ai-in-design-systems.netlify.app/)、[techniques](https://state-of-ai-in-design-systems.netlify.app/techniques)）。这份审计直接读各家仓库和发布包，可信度接近一手资料。但它只有 Kaelig Deloumeau-Prigent 一位审计者，而且是 7 月的快照，这一点要记住。领先者正在从“通过 MCP 提供文档”转向“提供 agent 必须调用的校验工具”。Polaris 在 skill 里内置 typecheck，最多重试 3 次，没通过就不许交代码。SLDS 有带自动修复和 SARIF 输出的 linter。Atlassian 的 `eslint-plugin-design-system` 号称“对人和 agent 都生效，且不耗 token”。Ant Design 要求每次编辑后都跑 `antd lint`（[Polaris](https://state-of-ai-in-design-systems.netlify.app/systems/shopify-polaris)、[SLDS](https://state-of-ai-in-design-systems.netlify.app/systems/salesforce-slds)、[Atlassian](https://www.atlassian.com/blog/how-we-build/atlassians-design-md-is-here-what-we-learned-testing-portable-design-context-in-practice)）。这类确定性检查真正装进使用方仓库的情况很少，每家只覆盖自己的系统；能跨系统检查渲染后页面视觉漂移的工具，目前还没有。

和 Atom63 最像的是 Astryx：Meta 出品，2026 年 6 月 18 日进入 beta，MIT 协议，基于 React 19 + StyleX，有 150 多个组件（[Astryx blog](https://astryx.atmeta.com/blog/introducing-astryx)）。`astryx build "<idea>"` 不调模型、不联网，确定性地检索模板。生成的 AGENTS.md 写着“每个页面都从模板开始”“不用裸 div”“只用 token，不写魔法值”等硬规则。它还有两个工具的托管 MCP 和 23KB 的 `manifest --json`（[Working with AI](https://astryx.atmeta.com/docs/working-with-ai)、[State of AI: Astryx](https://state-of-ai-in-design-systems.netlify.app/systems/astryx)）。对 Atom63 来说，`atom63 build`、模板、CLI+MCP 共用一个索引、vibe test，这些功能 Astryx 都有，而且有 Meta 的品牌背书。所以“我们有检索、规则和 vibe test”算不上差异点。更值得注意的是 Astryx 在仓库里留的 vibe test 夜间账本：**91 条记录里基线赢 50 次，Astryx 赢 19 次，Astryx+Tailwind 赢 9 次，平局 13 次**；其中“Design”维度由视觉模型对照 62 张参考图打分，说明文档没有公开（[State of AI: Astryx](https://state-of-ai-in-design-systems.netlify.app/systems/astryx)）。这份账本里“基线”到底指 shadcn/Tailwind 还是裸 HTML，审计记录没写清，不能直接当成“设计系统让 agent 变差”的证据。但它至少说明：在最接近的同类项目上，“用设计系统 vs 不用”的视觉评分持续偏向不受约束的一方。Atom63 单次 79 对 68 的结果，方向正好和这份 91 次的账本相反。在样本扩大之前，这个结果不该用来对外宣传。

Astryx 还有两点值得借鉴。第一，它对使用方只用自检提示词：让模型重读输出，替换掉 `className`、内联样式和硬编码值。据称这能把复杂任务里残留的裸 CSS 从约 11–13% 降到原来的四分之一，但各组的明细没有公开。确定性 lint 门禁只给贡献者用，审计原话是“执行路径上没有 LLM”。第二，它按实测给 API 起名：没有文档的那组 agent 在 8 次里有 5 次用了 `options`，于是 Selector 的 `items` 改名为 `options`（[State of AI: Astryx](https://state-of-ai-in-design-systems.netlify.app/systems/astryx)）。前一点正是 Atom63 的现状：craft 规则只在 DS 仓库的 CI 里跑，使用方项目只有 AGENTS.md 的文字约束。后一点给 F1 的组件改名提供了比“偏好 shadcn 命名”更可靠的方法，就是用 agent 的先验来定名。

Atlassian 发布的数据支持 Atom63 走“CLI 优先、按需检索”的路线。在登录页测试里，一份 80KB 的 DESIGN.md 用了 7.21M token、45.3 轮，而 MCP 只用 3.75M、35.1 轮。DESIGN.md 还会让 agent 重新造组件，而不是去 import `@atlaskit/button`。作者自己说这些结果“不是定论”（[Atlassian DESIGN.md](https://www.atlassian.com/blog/how-we-build/atlassians-design-md-is-here-what-we-learned-testing-portable-design-context-in-practice)）。他们的 CLI 和 MCP 相比，每个任务的时间和 token 各少约 8%。用 npx 调用时每次查询超过 15 秒，改成预装后开销少了 95%（[Atlassian CLI](https://www.atlassian.com/blog/ai-at-work/giving-ai-agents-design-system-context-from-the-terminal-what-we-learned-building-a-cli)）。对目标 2 来说，这意味着使用方项目应该预装 `atom63`，而不是每次 `npx`。

## lint 反馈是唯一实测有效的杠杆，而且 shadcn 已经做了

研究前的判断是“shadcn 没有使用方侧的强制机制”。按 7 月对 shadcn@4.15.0 的审计，这个判断成立：它的约束只有 skill 里的硬规则、MCP 的 `get_audit_checklist`，以及测试 skill 本身的 evals，没有任何东西进入使用方的 ESLint 或 CI（[State of AI: shadcn/ui](https://state-of-ai-in-design-systems.netlify.app/systems/shadcn-ui)）。但 9 月情况变了。**`@shadcn/lint`（2026-09-02 建仓，约 3.1k star）是“面向 agent 的 Tailwind 设计系统 linter”，不要求使用 shadcn/ui**，跑在 ESLint/Oxlint 上，规则包括 `no-raw-colors`、`no-unknown-classes`、`no-arbitrary-values`、`no-inline-styles`、`no-restyle`（[shadcn-ui/lint](https://github.com/shadcn-ui/lint)）。它在 150 多次任务运行中的结果如下：

| 模型 | 反馈前违规 | 反馈后违规 | 完成任务 |
| --- | ---: | ---: | ---: |
| Sonnet 5 | 69 | 0 | 8/8 |
| Haiku 4.5 | 66 | 0 | 8/8 |
| Opus 5 | 42 | 0 | 8/8 |
| GPT 5.6 Terra | 117 | 0 | 8/8 |
| GPT 5.6 Sol | 98 | 0 | 6/8 |

和只给规则文本相比，加上 lint 反馈后修正成本低 10%–48%。评测文档还说，“没有 linter，每个模型都会漂移”，即使提示词里完全没提样式也一样（[evals](https://github.com/shadcn-ui/lint/blob/main/docs/evals.md)）。这组数据是厂商自己发布的，任务都在“一个小型 shadcn 项目”里，测的是 shadcn 词汇内部的遵守程度，不是不同命名方案之间的比较。但它是目前公开资料里唯一量化了“确定性反馈对 agent 漂移有多大作用”的数据，结论也很清楚：违规接近归零，靠的是验证，不是词汇本身。

这同时证实并修正了 F2。证实的部分是：Atom63 的 starter 引入了完整 Tailwind，默认色板和任意值都能用，也没有 lint，使用方项目里只有 AGENTS.md 一层文字约束，而文字约束的效果已被多方证明不稳定，这正是最大的缺口。修正的部分是：按“不重复造轮子”的目标，`atom63 check` 不该从零写一套 Tailwind 类名 linter。它应该建立在 `@shadcn/lint` 之上，或者与它兼容：把 Tailwind 主题锁定到 `--a63-*` token 后，`no-unknown-classes` 和 `no-raw-colors` 能直接覆盖“乱用色板”和“编造类名”这两类问题。Atom63 只需要补上它独有的规则：物理属性改用逻辑属性、焦点环只用 `:focus-visible` 加 `outline`、优先复用组件。这些规则现在只在 DS 仓库里跑，F2 要做的是把它们打包带出去。agent 侧要照 Polaris 的做法写成硬约束：每次编辑后必须跑 check，有限次重试，不通过就不许交付（[Polaris](https://state-of-ai-in-design-systems.netlify.app/systems/shopify-polaris)）。“每个门禁检查都配一个已知错误样例”这条规则也有研究支撑：要证明一个检查真的能发现问题，就得用故意植入缺陷的样例来校准它（见下一节）。

## VLM 评审只能做参考，4 个 brief 什么也证明不了

F2 里的 `atom63 review`（截图 + rubric 打分）需要大幅收窄。最直接的证据来自 Luera 等人 2025 年 10 月的研究：30 个 UI、9 个维度、500 名众包评分者。Claude 3.5 Sonnet 的总体 Pearson 相关约 0.69，但精确命中只有 38%。**成对判断的准确率约 60%（Claude 59.98%，GPT-4o 59.60%）**，“易用性”这一维度只有 47–52%，等于随机；只有人类认为两者差距很大时，准确率才升到约 90–93%（[arXiv 2510.08783](https://arxiv.org/html/2510.08783v1)）。这篇论文测的是老一代模型，没有测换序，正文和表格里的数字还有不一致，所以只能当作方向性证据。PerceptUI 在 WiserUI-Bench 上发现现有 MLLM 对输入顺序很敏感，倾向于选第二张图（[arXiv 2606.05697](https://arxiv.org/pdf/2606.05697)）。自偏好偏差的研究表明，模型能认出自己的输出，认得越准，就越偏向自己（[NeurIPS 2024](https://papers.nips.cc/paper_files/paper/2024/hash/7f1f0218e45f5414c79c0679633e47bc-Abstract-Conference.html)）。不过那项实验做的是摘要任务，不是 UI。Atom63 现在由 Claude 生成、由 Claude 盲评，Atom63 的页面又有可辨认的统一风格，所以“盲评”挡不住风格识别。

验证做得最扎实的是 ArtifactsBench：渲染出页面，截取三张交互截图，按每个任务专属的 10 维清单打分，用两个不同家族的模型交叉评审。它的结果和 WebDev Arena 的排名一致性为 94.4%，和专家的成对一致性最高 90.95%（[arXiv 2507.04952](https://arxiv.org/html/2507.04952v2)）。注意，94.4% 衡量的是“模型排名的一致性”，不是单个判断的可靠性。UICrit 表明，给模型看专家点评作为 few-shot 示例，再在图上标出区域，UI 反馈的质量能提升 55%（[arXiv 2407.08850](https://arxiv.org/abs/2407.08850)）。把这些证据合起来，`atom63 review` 应该拆成两层。第一层是确定性一致性指标，用来做门禁：从渲染后 DOM 的 `getComputedStyle` 算出颜色、间距、圆角、阴影、字号中落在 token 刻度上的比例，每个属性出现了多少种不同取值，有多少“差 1–3px 没对齐”的边，再加上 axe 检查、键盘遍历检查焦点环、用 Playwright 驱动各种状态。第二层是 VLM 评审，只做参考，只评层级和构图这类无法用规则判断的维度。问法要从“给间距节奏打 1–3 分”改成“列出未对齐的元素并给出坐标”；比较类判断正反两个顺序各跑一次，只算两次结论一致的；同一页多次采样取中位数；评审模型最好换成非 Claude 家族。经典的界面美学指标最多只能解释人类审美评分 32%–51% 的方差（[Miniukovich & De Angeli](https://www.academia.edu/11396872/Quantification_of_Interface_Visual_Complexity)），所以一致性指标衡量的是“是否符合 Atom63”，不是“设计好不好”。两层缺一不可，但只有第一层能用来拦截。

现在 vibe test 的统计基础撑不起任何结论。79/84 对 68/84 的差距平均到每个 brief 约 2.75 分，可分析单位应该是 brief，不是 28 个评分项。同一个 brief 下的 7 项评分来自同一个页面、同一次评审，彼此不独立（[Anthropic: 给评测加误差条](https://www.anthropic.com/research/statistical-approach-to-model-evals)）。只有 4 个 brief 时，**就算 Atom63 四局全胜，配对符号检验的单侧 p 也只有 0.0625**；配对 t 检验只有 3 个自由度，要求差距非常稳定。Atom63 已经拿到 94% 的分数，接近满分，以后再改进也很难在分数上体现出来。rubric 里的“token 使用”“状态完整性”本来就偏向 Atom63，而且在截图里看不出来，这部分分差有一部分是 rubric 设计造成的。要让结果能当作质量证明（目标 1），需要做到这些：15–30 个固定版本的 brief，另留几个不参与调优；每组每个 brief 独立生成 3–5 次；按 brief 聚类、用 bootstrap 给出配对差的 95% 置信区间，同时报告胜/平/负；可以确定性测量的指标，从 rubric 里移到第一层。这些是从一般评测统计方法推出来的，没有找到针对 UI 评测的样本量研究。

还有一点要分清。Anthropic 说的“AI slop”是分布收敛导致的千篇一律，例如 Inter/Roboto 字体、白底紫色渐变、可预测的布局（[Claude blog](https://claude.com/blog/improving-frontend-design-through-skills)）。“Design Theater”研究发现，5 个生成工具做出的 120 个界面，在外观和布局上都趋同（[arXiv 2607.22928](https://arxiv.org/abs/2607.22928)）。设计系统能解决的是另一种 slop：间距、颜色、组件各写各的，前后不一致。对“千篇一律”，设计系统自己就可能变成新的收敛默认值。Astryx 输掉自家的 vibe test，很可能就是这个原因。所以 `atom63 review` 不应该在不知道项目品牌意图的情况下奖励或惩罚“独特性”。

## shadcn 角色名换来的是兼容性，Figma 重分层要绕开套餐和改名两道坑

F1 提议把 shadcn 角色名作为规范语义层。研究支持这样做，但理由和原来设想的不同。v0 的旧版 registry 流程要求“所有变量名保持不变”，还明说 v0“专门在 shadcn/ui 组件的默认实现上训练过”（[v0 legacy](https://v0.app/docs/design-systems-legacy)）。presets、主题生成器、第三方 Figma kit 也都以这套变量名为准。换句话说，**这套名字是生态里事实上的交换格式**。但目前**没有任何对照研究证明 shadcn 命名比自定义命名让 agent 出错更少**，“agent 认识 shadcn 名字”的说法多来自厂商宣传。`@shadcn/lint` 的数据反而说明：只要词汇能被机器校验，自定义名字最多多一轮修正。所以采用 shadcn 名字的理由是兼容生态、降低使用者的学习成本，不能写成“提高 agent 准确率”。shadcn 的词汇本身也有明显缺口：除了 `destructive` 没有其他状态色，当前脚手架里 `destructive` 也没有 `-foreground`；没有表面层级；`accent` 在 shadcn 里指悬停时的中性底色，在 Primer 里是蓝色品牌色，在 Atlassian 里是无语义的装饰色；`muted`、`input` 的含义也容易混淆（[shadcn Theming](https://ui.shadcn.com/docs/theming)、[Primer](https://primer.style/product/primitives/color/)、[Atlassian color](https://atlassian.design/foundations/color)）。合理的做法是：shadcn 现有的变量名一个都不改，再按同样的“角色 + `-foreground`”语法补齐 `destructive-foreground`、`success`/`warning`/`info`，以及少量表面层级和 `selected`。社区里 ReUI 已经在用前三个状态名（[ReUI](https://reui.io/docs/styling)）。最后把 `accent` 的含义写进文档并固定下来。

Figma 侧的证据支持 F1 的重分层方向，但划出了三条硬约束。第一，**分组依据是含义，不是个性化轴**。Figma 官方 agent skill 推荐的参考结构是 Simple Design System：7 个 collection、368 个变量，primitives 只有一个 mode，语义色分 light/dark 两个 mode；Primitives 设 `scopes = []`，不出现在任何选择器里（Figma 官方 agent skill `figma-generate-library` 的 `references/token-creation.md`）。Atom63 现在按轴分成 14 个 collection，`Semantic` 里只有 24 个变量，正是这一条的反例。第二，**套餐上限**：Professional 每个 collection 最多 10 个 mode，Organization 20 个；extended collections 只有 Enterprise 能用，在其他套餐上 Plugin API 会直接报错；变量的 REST API 只开放给 Enterprise；Code Connect 需要 Organization 或以上（[Compare plans](https://help.figma.com/hc/en-us/articles/360040328273-Compare-Figma-plans-and-features)、[Extended collections](https://help.figma.com/hc/en-us/articles/36346281624471)）。还有个坑：Figma 自家 skill 里写的仍是过时的 4/40 上限，加载这个 skill 的 agent 会拿到错误数字。不靠 Enterprise 的做法是用 alias 链：Semantic（light/dark）指向 Brand（品牌 mode），Brand 再指向 Primitives。Figma 在每一跳都用当前节点对该 collection 选中的 mode 来解析（[resolveForConsumer](https://developers.figma.com/docs/plugins/api/properties/Variable-resolveForConsumer)），但不支持让一个 collection 的 mode 由另一个 collection 推导出来（[论坛](https://forum.figma.com/suggest-a-feature-11/feature-request-let-a-variable-mode-be-derived-from-another-collection-s-mode-mode-mapping-57866)）。被跳过的 183 个双轴 token，根子在结构上：每条轴必须管一组互不重叠的 token。Dow Jones 的多品牌体系就没用 extended collections（[案例](https://medium.com/design-bootcamp/figma-variables-for-complex-multi-brand-systems-618845ac7ae6)）。第三，**改名会断引用**。理论上绑定跟着变量的 key 走，但论坛报告了字符串变量改名、collection 改名之后引用失效，发布后 API 还返回过时的 key（[改名断链](https://forum.figma.com/report-a-problem-6/renaming-collections-broke-references-to-variables-16434)、[过时数据](https://forum.figma.com/report-a-problem-6/figma-teamlibrary-returns-stale-library-variable-data-after-library-publish-update-52411)）。Plugin API 里也没有“保留 ID 移到另一个 collection”的方法。所以把 `action/primary` 从 Brand 移到 Semantic 是一次破坏性迁移，**只能做一次，越早做代价越小**。typography 和阴影仍然没有复合变量，只能做成绑定了变量的 text style 和 effect style。`use_figma` 还在 beta，写入需要 Full 席位，以后会改成按量收费，单次输出上限 20KB（[Write to canvas](https://developers.figma.com/docs/figma-mcp-server/write-to-canvas)、[MCP FAQ](https://help.figma.com/hc/en-us/articles/39252411778583-Figma-MCP-server-FAQs)）。因此生成器要做到幂等，按 DTCG 路径这样的稳定标识做 upsert，绝不先删后建。

DTCG 2025.10 的 Resolver Module 在 2025 年 10 月 28 日成为 Final CG Report，状态是“稳定”，但不是 W3C 标准，版本号字段在规范里前后矛盾（`2025-10-01` 和 `2025-11-01`）（[Resolver CG-FINAL](https://www.w3.org/community/reports/design-tokens/CG-FINAL-resolver-20251028/)）。工具支持很薄。Style Dictionary 官方说 2025.10“还没有完全支持”，也没提 resolver（[SD DTCG](https://styledictionary.com/info/dtcg/)）。Terrazzo 有 `createResolver`，但它自己的文档对哪个版本开始支持说法不一（[Terrazzo](https://terrazzo.app/docs/reference/js-api/)）。有实际用户报告 `tz check` 只检查默认 context（[PR](https://github.com/haaanju/pts/pull/6)）。Figma 原生的 DTCG 导入导出按 mode 逐个处理，不认 resolver（[Modes for variables](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)）。规范建议各 modifier 彼此正交，这和 Figma 的 alias 链模型一致：把 Atom63 的源文件改成正交结构，resolver 设计和 Figma 导出的问题能一次解决。但生成器必须留在自己手里，不能指望第三方工具接手。

## 按项目的三个目标重新排序

前面的证据对 F1–F4 的影响如下：F2 被证实，而且应该提前，但里面的 VLM 评审要降级为参考；F1 得到支持，但要拆开，其中“冻结词汇、把 token 轴正交化”必须排在 F2 前面，因为 `no-unknown-classes` 一类规则会把现有名字固化下来，先上 lint 再改名，就要改两遍；F4 受套餐约束，Code Connect 需要 Organization，extended collections 需要 Enterprise；F3 的价值被削弱，v0 已经把 shadcn registry 路线标成 legacy，改为直接导入任意设计系统（[v0 DS 2.0](https://v0.app/docs/design-systems-2)），Figma Make kit 也是走 npm 包而不是 shadcn registry（[Make kit](https://help.figma.com/hc/en-us/articles/43602872461079-Bring-your-design-system-package-to-a-Make-kit)），而且 F3 主要服务目标 3。

| 新顺序 | 范围 | 目标 1（商用级质量） | 目标 2（维护者自己的产品走 harness） | 目标 3（开源） | 研究依据 |
| --- | --- | --- | --- | --- | --- |
| 1 | **F1a 冻结词汇**：shadcn 角色名原样保留，补上状态/表面/`selected` 扩展；token 轴正交化，解决 183 个跳过的 token；一套主题 API | 高：架构正确性最容易被审视 | 前提：lint 和模板都依赖它 | 中 | lint 会固化词汇；resolver 和 Figma 都要求正交；改名只能做一次 |
| 2 | **F2 harness 进入自己的项目**：Tailwind 主题锁定到 token；`atom63 check` 基于或兼容 `@shadcn/lint`，加上 Atom63 独有规则；每个门禁配已知错误样例；agent 必须先跑 check 再交付；预装而不是 npx | 中 | **最高**：唯一实测能让漂移归零的手段 | 中 | shadcn lint 评测；Polaris/Ant 的循环；Atlassian 的 CLI 数据 |
| 2′ | **评测升级**（和 F2 同期）：确定性一致性指标做门禁，VLM 只做参考；vibe test 扩到 15–30 个 brief × 3–5 次，换用跨家族评审，报告置信区间 | **最高**：只有能复现的评测才算质量证明 | 高：用来判断 harness 是否真的有用 | 中：公开诚实的评测本身就是差异点 | Luera、ArtifactsBench、Miller；Astryx 账本 |
| 3 | **F1b Figma 重分层** + F4 中套餐允许的部分：按 SDS 结构分层，alias 链，生成器幂等；若套餐允许再做 Code Connect | 高：设计师能接受的 Figma 库是“商用级”的标志 | 中：取决于 Figma 在工作流里的角色（路线图定为草稿本） | 中 | Figma skill、套餐表、改名风险 |
| 4 | **F1c 组件命名统一**：按实测的 agent 先验来定名 | 中 | 中 | 中 | Astryx `items`→`options` |
| 5 | **F3 shadcn 分发** 和 F4 的其余部分（按原型生成组件、Figma 侧 lint）；iOS 维持伴随渲染器，不扩范围 | 低 | 低 | 高 | v0 不再依赖 registry；目标 3 优先级最低 |

这个排序有一个有力的反方观点：F3 的 `registry:base` 和 presets 也可以用来启动新项目，所以它对目标 2 也有用。这说得通，但 Atom63 已经有 app starter 和 16 个模板，`registry:base` 解决的是“起步时长什么样”，解决不了“之后会漂移”，而后者才是目标 2 的瓶颈（[CLI v4](https://ui.shadcn.com/docs/changelog/2026-03-cli-v4)）。另一个反方观点是：Astryx 输了自家的 vibe test，说明设计系统约束本身可能拉低视觉质量。这个风险应该用 2′ 的评测去验证，而不是靠放松约束来回避。iOS 方面，维护者的产品以 React + Vite + Tailwind 为主，iOS 倾向 SwiftUI，所以 iOS 维持伴随渲染器、按需拉动（路线图 N8）。

## 结论

研究改变的不是方向，而是两处因果判断。第一处：设计系统对 agent 的价值，从“提供正确的上下文”转向“对错误给出机器可读的反馈”。行业检索层已经趋同，没有哪家公开证明过“用设计系统让 agent 做得更好看”。被证明有效的只有一件事：确定性反馈能让违规接近归零。因此 Atom63 最有说服力的质量证明，是一套诚实的评测加上一套能带到其他项目里的门禁，而不是组件数量，也不是一次 79 比 68。第二处：词汇和 Figma 结构从“可以慢慢改”变成了有时间窗口的决定。lint 会把名字固化，Figma 改名会断引用，所以先冻结词汇，再接入门禁。

还有几处证据缺口：整个领域的横向数据几乎都出自一位审计者；`@shadcn/lint` 的效果是厂商自报，只在 shadcn 词汇内部测过；VLM 可靠性研究用的是上一代模型；没有任何研究直接比较过不同 token 命名对 agent 的影响。最便宜的下一步是在一个真实的使用方仓库里，用 `@shadcn/lint` 加锁定后的 Tailwind 主题跑一轮“有 lint 和没 lint”的对照。这一个实验就能同时回答目标 2 的可行性和目标 1 的证据问题。
