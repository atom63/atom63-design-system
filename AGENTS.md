# Agent guide: Atom63 design system

This repository is the Atom63 design system: one token architecture rendered in React, SwiftUI and
Figma. [CONTRIBUTING.md](./CONTRIBUTING.md) is the full contributor guide; this file is the short
version for coding agents.

## Where things live

| Path | Contents |
| --- | --- |
| `packages/styles` | `@atom63/styles`: DTCG token sources (`src/tokens/*.json`) and the CSS, manifest and Figma model generated from them |
| `packages/ui-foundation` | `@atom63/ui-foundation`: component contracts (`contracts/components/<name>.json`, which generate `src/components/<name>/<name>-contract.ts`) and the cross-renderer contracts |
| `packages/ui-react` | `@atom63/ui-react`: React components, recipes (`<name>.css`), stories and tests |
| `packages/ui-ios` | `Atom63UI`: SwiftUI components, shipped through the root `Package.swift` |
| `packages/mdx` | `@atom63/mdx`: MDX prose components and blocks |
| `packages/brand` | `@atom63/brand`: the ATOM63 logo components |
| `packages/inform` | `@atom63/inform`: the inform pattern (message registry, arbiter, and the banner, dialog, corner flyout and spotlight surfaces) |
| `packages/agent` | `@atom63/agent`: the headless agent (chat) runtime and its React hooks, with no UI |
| `packages/widgets` | `@atom63/widgets`: the widget foundation (units and scale, the widget card and surface, the loading, empty and error states, and the hosted shell) |
| `packages/cli` | `@atom63/cli`: the `atom63` CLI and MCP server that answer questions about the system |
| `apps/docs`, `apps/storybook`, `apps/figma-plugin` | Docs site, Storybook with render/axe/visual tests, Figma token sync |
| `scripts/design-system` | Audits, guardrails and the `ds:new` scaffold |

## How to work here

- **Look things up with `pnpm atom63`** (or the `atom63` MCP server from `.mcp.json`) before
  reading source: `pnpm atom63 component dialog`, `pnpm atom63 token --a63-surface-page`.
- **Add a component with `pnpm ds:new <name>`** (add `--ios` for a SwiftUI counterpart), not by
  copying one. `pnpm ds:new <name> --dry-run …` shows what it would change.
- **Change a token in its DTCG source**, then run `pnpm --filter @atom63/styles generate:tokens`.
  Never edit the generated CSS, manifest or Figma model by hand.
- **Change a component contract in its JSON source**
  (`packages/ui-foundation/contracts/components/<name>.json`), then run
  `pnpm --filter @atom63/ui-foundation generate:contracts`. Never edit the generated
  `*-contract.ts` or the component barrels by hand.
- **Regenerate instead of hand-editing** anything a `check:*` script writes: API reports
  (`pnpm api:report`), audits (`pnpm check:<audit> --write`), the craft baseline
  (`pnpm check:craft --write`), `utilities.css`, the agent index
  (`pnpm --filter @atom63/cli generate:index`) and the block below
  (`pnpm --filter @atom63/cli sync:agents-md`).
- **Verify the way CI does.** CI builds only some packages per job, so delete a workspace
  package's `dist` before checking code that newly imports it.
- **Score UI with the craft rubric** (`scripts/design-system/lib/craft-rubric.mjs`, docs page "Craft rubric").
- **Changesets:** a change to a published package (`@atom63/styles`, `@atom63/ui-foundation`,
  `@atom63/ui-react`, `@atom63/mdx`, `@atom63/inform`, `@atom63/agent`, `@atom63/widgets`,
  `@atom63/cli`; the list is `scripts/design-system/published-packages.mjs`) needs
  `pnpm changeset`; tooling-only changes need `pnpm changeset --empty`.
- **Releases need YZ's approval.** Merging the "Version Packages" pull request publishes to npm
  (beta tag). Do not merge it, run `pnpm release`, or dispatch the publish workflow without YZ's
  explicit approval.
- **Icons:** do not hard-wire ATOM63 brand icons into `ui-react`. Built-in icons come from
  `lucide-react`; where a component shows an icon, let the caller replace it.
- **Commits and pull requests:** Conventional Commit titles (`feat(scope): …`, `fix: …`), with
  English bodies that say what changed. `main` accepts pull requests only, and the `ci-status`
  check must pass.

## Building UI with Atom63

Ask the design system before writing UI, and start each screen with `atom63 build <idea>`, the idea in your own words. The `atom63` CLI and its MCP server (`atom63 mcp`) answer from the same generated index as the packages:

- `atom63 build <idea>`: a kit for what you are building: the closest page templates and blocks, the components they use, the foundation and the rules. For a phone screen it leads with `AppView layout="phone"` and a snippet to start from.
- `atom63 template <id>` and `atom63 copy <id> <dir>`: read a page or block template, then copy it and the blocks it uses into your project to adapt.
- `atom63 search <words>`: find a component, template, docs page, story example, token or public API name (a SwiftUI type or the export of a package entry point).
- `atom63 api <name>`: a SwiftUI type (`AtomWidgetCard`) or a JavaScript export (`MediaLightbox`, `KeyIdea`) with its import line and docs, and for an MDX block its purpose, an example and its props; an entry point (`@atom63/ui-react/media`, `Atom63UI`) with everything it exports.
- `atom63 component <slug>`: the import line, contract (axes, defaults, slots, states, web and iOS), related components and examples.
- `atom63 example <slug> [story]`: a known-good usage sample to start from.
- `atom63 token <name or words>`: a token with its values per theme and mode, Figma path and Swift name.
- `atom63 rules`: the rules below, with their reasons.

Add `--json` for a typed `{ type, data }` envelope. `atom63 manifest` lists every command and error code.

### Rules

1. Query the design system before writing UI: start a screen from the closest page template, then search for components, read their contracts, and start from story examples. The templates, catalog, contracts and examples are the reviewed answers; guessing reinvents them with drift. Not checked mechanically: it is a way of working, not a property of the code it produces.
2. Compose existing components before writing new ones. Add a component to the system with `pnpm ds:new`, not by copying another. A new component must be wired into contracts, recipes, docs and tests; the scaffold does that, a copy does not. Not checked mechanically: whether a new component was needed is a judgement; the vibe case studies report the share of elements taken from the system as a diagnostic.
3. Pass only the axis values a component's contract lists (sizes, variants, orientations), and rely on its defaults. Recipes, the SwiftUI renderer and the Figma variables are built for exactly those values. Not checked mechanically: each component's TypeScript props accept only the contract's values, so a type check rejects any other literal and no lint is needed.
4. Take every color, space, radius, shadow and duration from `--a63-*` tokens, and look a name up with `atom63 token` before using it. No literal colors and no Tailwind palette utilities. Paint text with `--a63-text-*` tokens and backgrounds with fill tokens, not the other way round. Tokens follow the theme, brand, mode and density; literals break all four, and a token name that does not exist resolves to nothing. In the design system repo, `check:craft` enforces it as `raw-color`, `unknown-token` and `token-role`.
5. Use the accent for one or two cues per view; the main action may be neutral. Give a view at most one `variant="primary"` Button. Selection is neutral by default; set `tone="accent"` on a selection, Slider or Progress only when it is one of those cues. Where the product draws its main action or its links in its brand colour, keep `variant="primary"` and `variant="link"`: sparing means one or two cues, not none. An accent on every control points at nothing. Button `default` is a high-emphasis neutral solid; `primary` is for a main action in the brand colour. Taking the accent off a product whose main action is brand-coloured loses the cue the product relies on. The vibe measures warn at more than one primary Button per file, and a case study with that warning is invalid.
6. Draw secondary actions in toolbars, list rows and card headers as `variant="ghost"` Buttons with `tone="muted"`, icon-only at `icon-sm` or `icon-xs` in dense rows. Keep the main action at full contrast. Muted ghost actions rest in the secondary text colour, with no box, and go to full contrast on hover, focus and press, so a row of actions stays calm and still answers the pointer. The vibe measures warn at a `variant="ghost"` Button with no `tone`; whether an action is secondary stays a judgement.
7. One boundary per element: border, fill or shadow, not two. Don't nest outlined containers. Each extra edge is another line to read past. Card `filled` and `elevated` and Button `raised` give a fill or a shadow without the border. Not checked mechanically: borders, fills and shadows add up across components and their parents at render time, so the source does not show the stack; it is left to review.
8. Controls drawn over photos or video use the `--a63-on-media-*` and `--a63-media-*` tokens. Theme colors are meaningless on an unknown picture; these hold contrast on any image. Not checked mechanically: whether a control sits over a picture is a layout fact the source does not show; it is left to review.
9. Draw content that carries its own colours (illustrations, game pieces, map and chart series, story rings, category marks) with the `--a63-category-{hue}` palette: 18 hues, each with `-subtle` and `-subtle-foreground`, as utilities such as `bg-category-green` and `text-category-green-subtle-foreground`. For another shade, mix two tokens with `color-mix(in oklch, var(--a63-category-green) 75%, var(--a63-text-primary))`, never a colour keyword or value. The palette follows the theme and the mode, so content stays legible in dark mode. A literal colour, or a keyword such as `black` inside `color-mix()`, fails `raw-color` and makes a vibe case invalid. In the design system repo, `check:craft` enforces it as `raw-color`.
10. Use logical properties and utilities (`margin-inline-start`, `ps-4`, `text-start`, `border-s`), not left and right. Layouts must mirror in right-to-left languages. In the design system repo, `check:craft` enforces it as `physical-properties`.
11. Draw focus rings on `:focus-visible` (`focus-visible:` in Tailwind), never on `:focus`. A pointer press should not leave a keyboard focus ring behind. In the design system repo, `check:craft` enforces it as `focus-visible`.
12. Draw focus rings as an `outline` (`focus-visible:outline-*` in Tailwind), not a `box-shadow` or `ring-*`. Inset it with a negative `outline-offset` where a parent clips it. A component's own box-shadow replaces a shadow ring, and forced-colors mode drops shadows. In the design system repo, `check:craft` enforces it as `focus-ring-outline`.
13. Never branch on light or dark mode in component code; let tokens and `UIProvider` resolve the mode. Themes and brands change the palette too; a mode check covers one axis of four. In the design system repo, `check:craft` enforces it as `mode-branch`.
14. A component you pass with `asChild` (or as `render`) must spread the props it receives onto the element it renders and forward its ref. The part merges its class, data attributes and ref into that element; a wrapper that drops them renders unstyled. Not checked mechanically: the component passed is your own code, and whether it spreads the props it receives shows only when it renders.
15. Keep the native semantics components render (buttons, links, labels, dialogs) and give every icon-only control an accessible name. Assistive technology reads the roles, states and names those elements carry. Every story runs axe in CI; code that removes semantics fails it.
