# Portfolio

This portfolio is built on the Atom63 design system. Components come from `@atom63/ui-react`,
tokens from `@atom63/styles`, long-form content from `@atom63/mdx`, the assistant from
`@atom63/agent` and the widgets from `@atom63/widgets`.

## Project

- `pnpm dev` runs the site; `pnpm typecheck` and `pnpm build` must pass before a change is done.
- `src/portfolio.config.ts` is the one config file: the person, the creative axes (brand, surface,
  radius, font), the hero plate and the optional modules. Read it first.
- Routes live in `src/router.tsx`. Every page is a child of `siteRoute`, which renders
  `src/components/site-layout.tsx`: the header, footer, assistant and dock, and the `data-a63-*`
  attributes from the config. A module's routes are added only when it is on.
- Content is in `src/content`: case studies in `projects/*.mdx`, posts in `writing/*.mdx` (the file
  name is the slug; `projects.ts` and `writing.ts` list the frontmatter fields), the resume in
  `resume.ts` and the timeline in `timeline.ts`. The sample content is about a fictional person;
  replace it rather than adding to it.
- MDX files can use the blocks in `src/components/mdx-components.tsx` without importing them. Add a
  block there.
- Optional modules live in `src/modules/<name>` and are switched in the config. Keep a module's code
  in its folder, and keep the site working with it off.
- The assistant's transport is `src/modules/assistant/transport.ts`. It answers offline from the
  content; a real transport calls the site's own server, never a model API with a key in the browser.
- `src/templates` holds the chat panel block the assistant draws with. It is the site's own code now.
- Mode and theme are set once in `src/theme.tsx` through `Atom63Theme`. Style with tokens and the
  Tailwind utilities mapped onto them (`bg-background`, `text-muted-foreground`, `border-border`).
- `npx shadcn add <component>` works (see `components.json`). Use it only for something the design
  system does not offer; its components pick up the same tokens through the shadcn bridge.

## Building UI with Atom63

Ask the design system before writing UI. Its documentation is published for agents:

- `https://system.atom63.io/llms.txt` lists every page with a one-line summary.
- Every page has a Markdown twin at its path plus `.md`, for example `https://system.atom63.io/components/component-dialog.md`. A component page gives the import line, the contract (axes, defaults, slots, states, web and iOS) and related components.
- Start each screen from the closest page or block template: `https://system.atom63.io/r/registry.json` lists them with a description each, and `npx shadcn add https://system.atom63.io/r/<id>.json` installs one with the blocks it uses.
- Start from a component that exists before writing markup of your own.

### Rules

1. Query the design system before writing UI: start a screen from the closest page template, then search for components, read their contracts, and start from story examples. The templates, catalog, contracts and examples are the reviewed answers; guessing reinvents them with drift. Not checked mechanically: it is a way of working, not a property of the code it produces.
2. Compose existing components before writing new ones. Add a component to the system with `pnpm ds:new`, not by copying another. A new component must be wired into contracts, recipes, docs and tests; the scaffold does that, a copy does not. Not checked mechanically: whether a new component was needed is a judgement; the vibe case studies report the share of elements taken from the system as a diagnostic.
3. Pass only the axis values a component's contract lists (sizes, variants, orientations), and rely on its defaults. Recipes, the SwiftUI renderer and the Figma variables are built for exactly those values. Not checked mechanically: each component's TypeScript props accept only the contract's values, so a type check rejects any other literal and no lint is needed.
4. Take every color, space, radius, shadow and duration from `--a63-*` tokens, and look a name up with `atom63 token` before using it. No literal colors and no Tailwind palette utilities. Paint text with `--a63-text-*` tokens and backgrounds with fill tokens, not the other way round. Tokens follow the theme, brand, mode and density; literals break all four, and a token name that does not exist resolves to nothing. In the design system repo, `check:craft` enforces it as `raw-color`, `unknown-token` and `token-role`.
5. Use the accent for one or two cues per view; the main action may be neutral. Give a view at most one `variant="primary"` Button. Selection is neutral by default; set `tone="accent"` on a selection, Slider or Progress only when it is one of those cues. Where the product draws its main action or its links in its brand colour, keep `variant="primary"` and `variant="link"`: sparing means one or two cues, not none. An accent on every control points at nothing. Button `default` is a high-emphasis neutral solid; `primary` is for a main action in the brand colour. Taking the accent off a product whose main action is brand-coloured loses the cue the product relies on. The vibe measures warn at more than one primary Button per file, and a case study with that warning is invalid.
6. Draw secondary actions in toolbars, list rows and card headers as `variant="ghost"` Buttons with `tone="muted"`, icon-only at `icon-sm` or `icon-xs` in dense rows. Keep the main action at full contrast. Muted ghost actions rest in the secondary text colour, with no box, and go to full contrast on hover, focus and press, so a row of actions stays calm and still answers the pointer. The vibe measures warn at a `variant="ghost"` Button with no `tone`; whether an action is secondary stays a judgement.
7. One boundary per element: border, fill or shadow, not two. Don't nest outlined containers. Each extra edge is another line to read past. Card `filled` and `elevated` and Button `raised` give a fill or a shadow without the border. Not checked mechanically: borders, fills and shadows add up across components and their parents at render time, so the source does not show the stack; it is left to review.
8. Controls drawn over photos or video use the `--a63-on-media-*` and `--a63-media-*` tokens. Theme colors are meaningless on an unknown picture; these hold contrast on any image. Not checked mechanically: whether a control sits over a picture is a layout fact the source does not show; it is left to review.
9. Draw content that carries its own colours (illustrations, game pieces, map series, story rings, category marks) with the `--a63-category-{hue}` palette: 18 hues, each with `-subtle` and `-subtle-foreground`, as utilities such as `bg-category-green` and `text-category-green-subtle-foreground`. Chart series take `--a63-chart-1` to `--a63-chart-5`, which keep apart from the brand; the `Chart` component reads them for you. For another shade, mix two tokens with `color-mix(in oklch, var(--a63-category-green) 75%, var(--a63-text-primary))`, never a colour keyword or value. The palette follows the theme and the mode, so content stays legible in dark mode. A literal colour, or a keyword such as `black` inside `color-mix()`, fails `raw-color` and makes a vibe case invalid. In the design system repo, `check:craft` enforces it as `raw-color`.
10. Use logical properties and utilities (`margin-inline-start`, `ps-4`, `text-start`, `border-s`), not left and right. Layouts must mirror in right-to-left languages. In the design system repo, `check:craft` enforces it as `physical-properties`.
11. Draw focus rings on `:focus-visible` (`focus-visible:` in Tailwind), never on `:focus`. A pointer press should not leave a keyboard focus ring behind. In the design system repo, `check:craft` enforces it as `focus-visible`.
12. Draw focus rings as an `outline` (`focus-visible:outline-*` in Tailwind), not a `box-shadow` or `ring-*`. Inset it with a negative `outline-offset` where a parent clips it. A component's own box-shadow replaces a shadow ring, and forced-colors mode drops shadows. In the design system repo, `check:craft` enforces it as `focus-ring-outline`.
13. Never branch on light or dark mode in component code; let tokens and `UIProvider` resolve the mode. Themes and brands change the palette too; a mode check covers one axis of four. In the design system repo, `check:craft` enforces it as `mode-branch`.
14. A component you pass with `asChild` (or as `render`) must spread the props it receives onto the element it renders and forward its ref. The part merges its class, data attributes and ref into that element; a wrapper that drops them renders unstyled. Not checked mechanically: the component passed is your own code, and whether it spreads the props it receives shows only when it renders.
15. Keep the native semantics components render (buttons, links, labels, dialogs) and give every icon-only control an accessible name. Assistive technology reads the roles, states and names those elements carry. Every story runs axe in CI; code that removes semantics fails it.
