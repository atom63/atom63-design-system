# Typography

The type system targets dense information interfaces rather than marketing pages. Body text starts at 15px—between compact 14px UI conventions and the browser's 16px default—to balance information density with sustained reading.

## Design intent

I wanted a scale that serves three very different surfaces from the same tokens: portfolio pages with expressive display type, documentation with dense readable prose, and app panels with compact controls. The solution is one responsive scale plus an independent `--typography-scale` multiplier that any subtree can adjust.

The shipped scale is deliberately not fluid. It uses viewport breakpoints for pages and `data-window-size` overrides for OS windows, so a constrained window can use its own size band even on a wide viewport. The separate `data-a63-type-scale` axis adjusts the whole ramp for user preference.

## Font families

| CSS variable | Tailwind | Stack |
|--------------|----------|-------|
| `--font-family-sans` | `font-sans` | Geist, system UI |
| `--font-family-serif` | `font-serif` | Brawler, Georgia |
| `--font-family-mono` | `font-mono` | Geist Mono, monospace |

I chose Geist because it's optimized for interfaces — generous x-height, clear at small sizes, and a mono companion that shares the same metrics. Brawler is reserved for rare editorial moments in the portfolio; the system defaults to sans everywhere.

## How the scale works

Sixteen steps from `2xs` (11px) to `11xl` (56px). Up to `9xl` (39px at mobile, 49px at `768px+`) the scale grows at `640px` and `768px`, and `[data-window-size='xs'|'sm'|'md'|'lg'|'xl']` applies the same bands inside OS windows; the two display steps, `10xl` (40px) and `11xl` (56px), stay the same at every width.

## Mental model

Typography has three separate jobs:

| Job | What it controls | Examples |
|-----|------------------|----------|
| Reading | Long-form comfort | Prose, docs, descriptions |
| Hierarchy | Relative importance | Page titles, section headers, labels |
| Density | How much interface fits | Sidebars, tables, controls, OS windows |

Do not solve all three with one heading scale. A docs page, a compact sidebar, and a portfolio hero need different hierarchy even when they share the same tokens.

### Line-height strategy

Body text (`xs` through `lg`) uses a ~1.5× ratio for comfortable reading. Display sizes (`xl` and above) compress to ~1.25× — tighter line-height at large sizes prevents headings from floating away from their content.

### The scale multiplier

`--typography-scale` defaults to `1`. The shipped `data-a63-type-scale` values map to `0.9` (`compact`), `1` (`normal`), `1.1` (`comfortable`), and `1.2` (`large`). OS window width is handled separately by `data-window-size`; the multiplier is a personalization control, not the window breakpoint mechanism.

## Decisions worth knowing

### 15px base, not 16px

Most systems use 16px because browsers default to it. I chose 15px after testing information-dense layouts — docs tables, prop references, sidebar navigation. At 16px, content felt loose and wasted space. At 14px, extended reading got fatiguing. 15px is the sweet spot for my use cases: dense enough for tool interfaces, comfortable enough for documentation prose.

### Breakpoints over fluid

Fluid typography (`clamp()`) assumes the viewport is the right proxy for text size. In the OS metaphor, multiple windows have arbitrary widths on one screen. Breakpoint jumps plus `data-window-size` attributes let window content follow its container band instead of the outer viewport.

### No heading-element-to-scale mapping in CSS

I don't automatically map `h1` to `9xl` or `h2` to `8xl` in the base tokens. Different surfaces need different heading scales — a docs `h2` should be smaller than a portfolio `h2`. The MDX variants handle heading sizing per context, and the raw scale stays available for explicit use via `text-*` utilities.

### Visual hierarchy and semantics are separate

A semantic `h2` does not always need to look like the second-largest text on the page. The `SectionHeader` pattern follows this rule: `variant` controls visual scale, while `level` can control document outline. That keeps accessibility and visual rhythm from fighting each other.

## Text roles

Text roles name what text is for, after the Apple HIG text styles, so one intent works on every platform. Each role picks a step of the scale on the web and a `Font.TextStyle` (with Dynamic Type) on iOS. The source is `packages/styles/src/tokens/type-roles.resolver.json`; each role has `--a63-type-<role>-font-size`, `-line-height`, `-font-weight` and `-font-weight-strong`, and the Tailwind utilities `text-<role>` and `text-<role>-strong` set all three at once.

| Role | Web step | iOS text style |
|------|----------|----------------|
| `display-large` | `11xl`, weight 600 | 56pt, scaled like `largeTitle` |
| `display` | `10xl`, weight 600 | 40pt, scaled like `largeTitle` |
| `large-title` | `6xl` | `largeTitle` |
| `title-1` | `5xl` | `title` |
| `title-2` | `3xl` | `title2` |
| `title-3` | `2xl` | `title3` |
| `headline` | `base`, weight 600 | `headline` |
| `body` | `base` | `body` |
| `callout` | `base` | `callout` |
| `subhead` | `sm` | `subheadline` |
| `footnote` | `xs` | `footnote` |
| `caption-1` | `xs` | `caption` |
| `caption-2` | `2xs` | `caption2` |

`-strong` is the emphasized weight: bold for the display roles, `large-title`, `title-1` and `title-2`, semibold for the rest. The display roles are for balances, prices and hero headlines; iOS has no larger text style, so `AtomDisplayRole` draws them at the web size and scales it with Dynamic Type like `largeTitle`. For an amount such as `$13.25`, use `Amount` from `@atom63/ui-react` (`<Amount value={13.25} currency="USD" />`, `size="lg"` for `display-large`): it formats the value for the locale with `Intl.NumberFormat`, draws the fraction at half size and raised with tabular figures, and reads as one label. `fraction="baseline"` keeps the half-size fraction on the baseline of the integer digits instead, as some banking apps draw a balance; `raised` is the default. Without the component, put the whole number in one `text-display tabular-nums` span and wrap the fraction in `amount-fraction`, which sets it at half size and raises it, or in `amount-fraction-baseline`, which sets it at half size on the baseline. On iOS, `AtomAmountText(13.25, currencyCode: "USD", role: .display)` formats the amount for the locale, draws the fraction the same way with monospaced digits and reads as one VoiceOver label, and `fraction: .baseline` keeps it on the baseline; `.atomDisplayFont()` sets a display role on any other text. Web sizes follow web conventions (body is 15px; iOS body is 17pt); the role is what stays the same. Size steps are fine while exploring; settled UI should use roles.

## Phone screens

The web scale is set for pages and desktop apps: body is 15px and compact control labels are 12–13px. A phone app screen reads at the iOS sizes instead, so `[data-a63-form-factor="phone"]` gives a subtree the type steps and control sizing of a phone. `AppView layout="phone"` (the app-view page template) stamps it on the screen; stamp it yourself on the root of a phone-only web app. Viewport width does not apply it, so a docs page or a marketing page on a phone keeps the web sizes.

| Role | Web, under 640px | Phone (`data-a63-form-factor="phone"`) | iOS text style |
|------|------------------|-----------------------------------------|----------------|
| `body`, `headline`, `callout` | 15px | 17px | `body` 17pt |
| `subhead` | 13px | 15px | `subheadline` 15pt |
| `footnote`, `caption-1` | 12px | 13px | `footnote` 13pt |
| `caption-2` | 11px | 11px | `caption2` 11pt |
| `title-3` | 19px | 20px | `title3` 20pt |
| `title-2` | 21px | 22px | `title2` 22pt |
| `title-1` | 26px | 28px | `title` 28pt |
| `large-title` | 28px | 34px | `largeTitle` 34pt |
| `display`, `display-large` | 40px, 56px | 40px, 56px | `AtomDisplayRole` |

The scope sets the steps themselves (`text-sm` is 15px and `text-base` 17px inside it), redeclares the text roles, and sizes controls the iOS way: heights of 36, 40, 44, 48 and 52px, and every standard control label (buttons, rows, fields, menus) at body size, with `xs` at footnote size for badges, shortcuts and initials. The secondary line under a title or label (an Item, Field or Form description, a Frame or ConnectedPanel description) reads `--a63-control-font-size-secondary`, which the phone scope sets to subhead size (15px) so it stays below its 17px title; elsewhere it falls back to the control `sm` size. The type scale preference still multiplies the phone steps. Inside a phone screen, keep rows and labels on the component defaults or the text roles; shrinking them with `text-sm` or `text-xs` brings back the desktop sizes.

## Usage guidance

| Surface | Typical range | Scale multiplier |
|---------|---------------|------------------|
| Portfolio hero | `4xl`–`9xl` | Usually `normal`; user preference still applies |
| Documentation prose | `sm`–`xl` | `1` |
| App panels / OS windows | `xs`–`lg` | Window-size band + active type-scale axis |
| Code blocks | `sm` mono | `1` |

## Anti-patterns

```tsx
// Avoid: viewport-sized type inside a constrained panel.
<aside className="w-80">
  <h2 className="text-5xl">Settings</h2>
</aside>
```

The panel is narrow even if the viewport is wide. The text should respond to the container's role, not the browser width.

```tsx
// Prefer: choose a scale for the surface.
<aside className="w-80">
  <h2 className="text-lg font-semibold">Settings</h2>
</aside>
```

## Review checklist

When reviewing typography, ask:

1. Is this text sized for its container, not only the viewport?
2. Does the hierarchy still work if the content wraps?
3. Is the line-height comfortable for the amount of reading?
4. Are semantic heading levels valid independent of visual size?
5. Is display type reserved for display moments?
